Overview

Cloud projects,
under control.

Kion connects the request, the cloud account and the cost owner in one operating process.

Request the environment

The project submits its cloud provider, environment, technical owner and cost center through HelpDesk. The budget owner approves the request before Cloud Operations starts provisioning.

The approved request defines the account purpose, access requirements and the team responsible for ongoing costs.

Apply the baseline

Kion places the account in the agreed project scope, assigns access roles and applies Cloud Rules. Logging, regional restrictions and required tags become part of the account baseline.

Cloud Operations checks the baseline before handing the environment to the project team.

Operate with visibility

The team runs its workloads in AWS, Azure or GCP. Kion brings billing and governance data back to the project owner, showing spend, forecasts and policy findings.

Finance and engineering use the same account ownership and cost allocation model.

Operational integration

HelpDesk records the request and approval. CMDB records the account, service and owner. Kion manages the account baseline.

Financial integration

Provider billing feeds Kion. Project mapping and tags allocate costs. The owner reviews exceptions and optimization actions.

Deployment architecture

Self-hosted
in our AWS.

  • Dedicated kion-prod account in Shared Services, isolated from the management account
  • Amazon ECS across availability zones and Aurora MySQL encrypted with KMS
  • Corporate access through TGW / VPN and internal ALB + WAF; SAML sign-in with Entra ID
  • Cloud connections use STS AssumeRole, Azure Service Principal and GCP Service Account

Architecture

Every choice
has a reason.

The proposed deployment keeps access, data and operational changes within a clear ownership model.

Self-hosted on AWS

Cloud Operations manages the installation, network perimeter, upgrades and backups. The operating model follows the company’s existing AWS environment.

The platform’s operational and financial data stays in company-managed infrastructure.

A dedicated account

kion-prod belongs to Shared Services. Separating the platform from the management account limits the scope of a platform incident.

Integration roles, network changes and privileged access can be audited independently.

ECS on EC2

Containerized services run on company-managed compute. Nodes span availability zones to reduce dependence on one location.

Capacity and upgrade procedures remain part of the Cloud Operations runbook.

Aurora with a reader

A writer and reader support recovery from a database or availability-zone failure. KMS protects stored data.

Backups and restore procedures need their own verification before service handover.

Internal ALB and WAF

Users reach the interface through the corporate network. The load balancer provides the controlled entry point for UI and API traffic.

The database has no direct user-facing access path.

Configuration in Git

Cloud Rules, project configuration and Spend Plans follow a reviewed change process. Each change records its purpose and intended scope.

Version history provides the source for rollback and explains why the configuration changed.

Network diagram

Private
by design.

  • VPC kion-prod separates public egress, application, data and endpoint subnets
  • The ALB is internal; public subnets contain NAT gateways for controlled egress
  • Development centers connect through Transit Gateway and site-to-site IPsec VPN
  • Outbound provider API traffic uses HTTPS; the corporate network has no direct route to the database

Access

The right access,
for each role.

Corporate identity establishes who a person is. Kion permissions define what that person can see and change.

Corporate sign-in

Entra ID authenticates users through SAML SSO and MFA. Group membership connects the corporate identity to an agreed Kion role.

A change of team or employment status triggers access review. Emergency access follows a separate procedure.

Project permissions

Project owners see the accounts and costs they are responsible for. Operators manage platform configuration within their assigned scope.

Budget approval and policy administration belong to different responsibilities.

Cloud access

Users enter cloud accounts through an approved Cloud Access Role. Platform administration has separate privileges.

Access grants and administrative changes leave an audit record.

Access

One platform.
Separate cloud identities.

Each connection has a defined trust relationship, permission scope and operational owner.

AWS · AssumeRole

Kion assumes an integration role in the target account. The trust policy and External ID define who can use it. Permissions cover the agreed billing and governance operations.

Connection checks include role trust, billing access, allowed actions and an auditable test call.

Azure · Service Principal

A dedicated identity receives access at the approved tenant and subscription scope. Billing access and resource permissions are reviewed as separate requirements.

Cloud Operations records credential ownership, expiration and the procedure for rotation.

GCP · Service Account

A service account connects the approved project and billing sources. Billing export access and resource-management permissions follow their own scope.

Changes to permissions or billing configuration are recorded and checked before extending coverage.

Read operations

Collect billing and resource metadata, validate ownership tags, and identify policy findings or idle resources.

Control operations

Provision accounts, apply approved rules and manage access. Automated actions are limited to agreed environments and scopes.

Account Vending

From request
to a ready account.

Account Vending connects approval, provisioning and handover. Every step produces a verifiable result.

  1. 01

    Request

    HelpDesk captures the provider, environment, project owner and cost center.

    ResultA complete request with a technical contact and an agreed purpose.

  2. 02

    Approve

    The budget owner approves the request. Cloud Operations checks the technical requirements.

    ResultRecorded approval and a defined provisioning scope.

  3. 03

    Provision

    Kion creates the account or subscription in the agreed project scope.

    ResultAn account identifier linked to the project. A failed creation stops handover.

  4. 04

    Verify

    Cloud Rules apply the access, logging, tagging and regional baseline.

    ResultCloud Operations checks that the required baseline is in place.

  5. 05

    Hand over

    The team verifies SSO access. The account enters CMDB and reporting.

    ResultConfirmed access, an accountable owner and a support route.

Required before provisioning

An owner, project and cost center must be known. Missing information returns the request to its author.

Required after handover

Kion continues to collect spend and policy findings. The project owner remains responsible for exceptions and follow-up actions.

Controls at each stage

Account ownership
Keep the project, technical contact and cost center current when teams or services change.
Policy exceptions
Record the affected scope, reason, approver and review date. Revisit exceptions when their purpose ends.
Unassigned costs

Change evidence
Keep the request, configuration history and audit event linked so support can reconstruct what happened.

Dataflow diagram

Every flow,
under TLS.

Cost allocation

Every cost
has an owner.

Allocation preserves the source record and explains how the amount reaches a project or department.

Source billing

AWS CUR, Azure Cost Management and GCP Billing provide account, service, resource and usage-period data. Ingestion retains the source of each record.

Late provider adjustments return through the same reconciliation process.

Project allocation

Account mapping identifies the project. Tags add owner, environment and cost center. Shared services use an allocation rule approved by the service owner.

Approved SaaS and AI imports enter the model through Custom Accounts.

Owner reporting

Project owners see direct costs, allocated shared costs and unresolved items. Finance receives the same model for consolidated reporting.

Cloud Operations reconciles Kion totals with provider billing before treating the reporting period as complete.

Missing tags or mapping

Keep the cost in a visible correction queue. Assign an owner to resolve it before moving it into a project report.

Shared accounts

Document the allocation basis and approval. A changed allocation rule must remain explainable across reporting periods.

Optimization

Insight becomes
a team action.

FinOps is complete when a recommendation leads to a reviewed change and a measured result.

  1. 01

    Observe

    Bring spend, tags, plans and forecasts together.

    Context includes the account, service, resource, environment and responsible team.

  2. 02

    Understand

    Check idle resources, sizing and unexpected growth.

    Review workload changes and seasonality before recommending a change.

  3. 03

    Assign

    Send the recommendation to the resource owner.

    The action includes a technical contact, affected resource and reason for review.

  4. 04

    Change

    The team approves the action through its change process.

    Production changes include a recovery plan. Automation stays within approved scope.

  5. 05

    Verify

    Compare the next billing data with the expected result.

    Close the recommendation using evidence after the change, not the ticket status alone.

Spend Plans

A spending plan.
A clear response.

Actual spend and forecasts determine who is notified and which actions are permitted.

Measure

Kion compares actual spend and forecast with the project Spend Plan. The plan identifies the funding source, period and accountable owner.

Changes to the plan retain the approval history and the reason for the adjustment.

Notify

The project owner and approver receive the affected account, the reason for the trigger and the information needed to investigate.

HelpDesk captures the team’s response and any request to adjust the plan.

Respond

Financial Enforcement applies only to an agreed scope. The environment determines whether the response is a notification or an approved control action.

Cloud Operations checks the outcome and can restore the previous configuration.

EnvironmentPermitted responseSafeguard

Cloud Rules

A shared baseline.
Controlled exceptions.

Cloud Rules express the intended account state. Scope and inheritance determine where each rule applies.

Company baseline

Audit logging
Enable provider audit logs and monitor attempts to disable them. Forward the required events to the security platform.
Approved regions
Restrict deployment to the agreed regions. Review a new region before extending the account baseline.
Security services
Apply the approved provider security configuration and check that the services remain enabled.
Ownership tags
Require owner, project, environment and cost center so resources remain attributable.
Access guardrails
Control long-lived keys, privileged access and public storage exposure through reviewed provider policies.

Environment controls

Development limits
Apply the approved resource families and sizes where the development team can operate safely.
Operating schedules
Use agreed shutdown schedules for eligible non-production resources. Exclusions have an owner.
Cloud access roles
Use the approved access model for shared services and review privileged role assignments.
Client isolation
Keep client accounts outside the initial internal scope until Security and Legal approve the design.
Financial enforcement
Apply restrictive actions to approved non-production scope. Production follows its escalation process.

Policy as code

Policies ship
through review.

A rule reaches its target accounts only after its scope, impact and recovery path have been checked.

  1. 01

    Change

    Describe the Cloud Rule and target scope in Git.

    The pull request states the reason, intended accounts, expected result and rollback steps.

  2. 02

    Review

    Cloud Operations and InfoSec assess the change.

    Check access permissions, workload dependencies and potential deployment failures.

  3. 03

    Test

    Apply the rule to a Sandbox OU.

    Verify an allowed action, a blocked action and restoration of the previous state.

  4. 04

    Release

    Promote the approved change to a test group of accounts.

    Broader rollout depends on observed results. Production begins with monitoring.

  5. 05

    Monitor

    Review findings, failed actions and the audit trail.

    Repeated failures stop the rollout and return the change to the rule owner.

Rollback

Restore the previous configuration from Git. Keep the failure, recovery action and verification linked in HelpDesk.

Exception

Record the owner, affected scope, reason and review date. Revisit the exception when its purpose or environment changes.

Security

Clear trust boundaries.
Consistent controls.

Network entry
The corporate network reaches the internal ALB. UI and API use the controlled platform entry point.
Identity
Entra ID authenticates the person through SAML and MFA. Kion maps the person to the approved role.
Authorization

Privileged operations

Administration

Secrets and storage

Audit
Splunk receives sign-in, policy-change and role-use events so security can reconstruct administrative activity.

User boundary

SSO, MFA and project-scoped permissions.

Platform boundary

Dedicated account, private subnets and verified recovery.

Provider boundary

Separate integration roles with reviewed trust and permissions.

Monitoring

When something fails,
support can see it.

Monitoring covers service health, data freshness and the outcome of control actions.

Platform health

Monitor the UI, API, ECS services, Aurora and backup jobs. Background ingestion needs its own success and freshness checks.

A responsive dashboard does not prove that the underlying billing data is current.

Cloud connections

Track failures in AssumeRole, Service Principal and Service Account connections. A permission or credential change can interrupt collection.

The alert identifies the affected provider, account and source so the operator can investigate.

Governance events

Capture rule changes, failed enforcement actions, tagging findings and spend anomalies. Retain the actor, scope and outcome.

Security and operations use the same audit evidence to reconstruct the sequence of actions.

Rollout

Roll out
in dependency order.

Each phase produces evidence that the next phase can proceed safely.

  1. 01

    Platform

    Deploy kion-prod, VPC, ECS, Aurora, KMS and secret storage. Enable backup and monitoring.

    ExitAn available installation with a verified restore procedure and an infrastructure owner.

  2. 02

    Access

    Connect SSO, RBAC and privileged access. Start Cloud Rules in Sandbox and enable audit delivery.

    ExitTested user, operator and administrator roles with working audit records.

  3. 03

    AWS pilot

    Connect pilot accounts and billing. Check tagging, Spend Plans and Account Vending.

    ExitReconciled spend, a successful account handover and a tested policy rollback.

  4. 04

    Extend

    Connect HelpDesk and CMDB. Add the remaining AWS scope, then Azure, GCP and approved custom imports.

    ExitA clear ownership, data and support model for every additional source.
